# PMC — Workflow для backend-команды

> Эта инструкция объясняет, как backend-команда работает в одной связке с frontend (Claude / Антон) и тестировщиком. Все три стороны координируются через [`BUG_TRACKER.md`](BUG_TRACKER.md). Других каналов (чат, отдельные тикеты, Slack-треды) нет — всё пишется сюда.

---

## TL;DR

1. Один раз в начале раунда прочитать [`BUG_TRACKER.md`](BUG_TRACKER.md) сверху до низа. Это backlog текущего раунда.
2. Брать только тикеты с `Owner: BE` или `Owner: FE+BE` (со стороной BE).
3. Перед началом работы — пометить `🟧 In progress` + `Assignee`.
4. По завершении — `🟩 Done (awaiting QA)` + строка в `History` с датой, коммитом/PR, кратким описанием решения.
5. Не закрывать тикет в `✅ Closed` самостоятельно — это право тестировщика после верификации.

---

## Что читать в трекере

В таблице **Index** (вверху файла) — все открытые тикеты раунда с статусами и владельцами. Фильтры, которые касаются BE:

| Owner | Когда брать |
|-------|------------|
| `BE` | Только backend — frontend ничего не делает, ждёт деплоя. |
| `FE+BE` | Совместная работа. FE и BE могут идти параллельно, но FE-сторона часто блокируется до появления API. |
| `FE` | **Не брать.** Это работа frontend (Claude / Антон). |
| `PM` | **Не брать.** Нужно продуктовое решение до старта работ. |

Severity подсказывает приоритет:
- 🔥 **Critical** — берём в первую очередь, особенно privacy / money / data loss.
- 🟠 **Major** — основная масса, плановая работа.
- 🟡 **Minor** — после Major.
- 🔵 **Polish** — когда есть свободные руки.

## Жизненный цикл BE-тикета

### 1. Заявить работу (изменить `Status` и `Assignee`)

Открыть секцию тикета в `BUG_TRACKER.md`, поправить header:

```diff
- **Severity:** 🔥 Critical · **Status:** 🟥 New · **Owner:** FE+BE · **Assignee:** —
+ **Severity:** 🔥 Critical · **Status:** 🟧 In progress · **Owner:** FE+BE · **Assignee:** {ваше_имя} {YYYY-MM-DD}
```

Закоммитить это изменение **отдельно от кода** — `chore: claim BUG-XXX`. Чтобы FE сразу видел, что тикет в работе и не дублировал.

### 2. По ходу работы — короткие строки в `History`

Если работа растягивается на несколько дней / упёрлась в неожиданность — раз в день оставлять строку:

```markdown
### History
- 2026-05-26: создан Антоном.
- 2026-05-27 · Иван · приступил, начал с миграции схемы.
- 2026-05-28 · Иван · миграция готова (commit a3f4c2d), upgrade-path для legacy bookings не покрывает edge-case с null contract.signedAt — обсуждаем с PM.
```

Не комитить «WIP» в History без сути. Цель — чтобы при ротации разработчиков следующий человек **не задавал вопросов**.

### 3. При блокере — `🟨 Blocked`

Блокер бывает трёх типов:

- **FE не отдал прецеденты / payload** → `Status: 🟨 Blocked`, в History: `ждём пример запроса от FE: какие именно поля приходят в X`.
- **Продакт не определился** → `Status: 🟨 Blocked`, тег `@PM`, конкретный вопрос.
- **Внешний сервис лежит** → `Status: 🟨 Blocked`, описать что именно сломано и где видно.

Блокированный тикет — **не ваша проблема**. Он висит на блокирующей стороне.

### 4. Завершение — `🟩 Done (awaiting QA)`

После deploy:

```diff
- **Severity:** 🔥 Critical · **Status:** 🟧 In progress · **Owner:** FE+BE · **Assignee:** Иван 2026-05-27
+ **Severity:** 🔥 Critical · **Status:** 🟩 Done (awaiting QA) · **Owner:** FE+BE · **Assignee:** Иван 2026-05-27
```

В `History` обязательно:

- **Дата + ник.**
- **Что сделано в двух фразах** (НЕ копипаста коммит-сообщения — нужно объяснить логику решения).
- **Ссылка на коммит / PR / merge-commit** (`commit a3f4c2d` или PR-номер).
- **Что изменилось в API-контракте.** Если поменялся response — обновить пример в `Acceptance criteria` (или добавить).
- **Что нужно от FE / QA для верификации** (если есть нюансы вроде «нужно прогнать миграцию руками» / «протестить под тенант-аккаунтом X»).

Пример:

```markdown
- 2026-05-28 · Иван · готово (PR #347). Добавил domain event `BookingRequestApproved` →
  `NotificationService.Notify(landlordId, ...)`. Notifications пишутся в новую таблицу
  `Notifications` (миграция 0067_notifications). Эндпоинты GET /api/me/notifications +
  PATCH /api/me/notifications/{id}/read доступны. Email / push временно отключены
  (через `notificationPreferences.disabledChannels`) — включим в следующем раунде.

  Контракт response (`GET /api/me/notifications`):
  ```json
  {
    "items": [
      { "id": "uuid", "kind": "BookingRequestApproved", "bookingId": "uuid",
        "title": "...", "body": "...", "isRead": false, "createdAt": "ISO" }
    ],
    "unreadCount": 3
  }
  ```

  QA: проверять под landlord-аккаунтом Marina после approve тестовой заявки.
```

### 5. Если QA вернул тикет (`🟥 Reopened`)

Не возмущаться, не спорить в комментариях кода. Открыть тикет, прочитать причину в History, **диагностировать на основании конкретного шага**, где сломалось. Если шаг непонятен — попросить QA уточнить через ту же `History`-строку (один обмен в день).

После повторного фикса — снова `🟧 In progress` → `🟩 Done`.

---

## Что нельзя делать

- **Не закрывать тикет в `✅ Closed (verified)` самостоятельно.** Это прерогатива тестировщика. Backend может проверить юнит-тестами что endpoint работает, но «работает» != «пользовательский сценарий чинится».
- **Не менять `Owner` тикета без согласования** с FE/PM. Если выяснилось, что это чисто FE — написать в History `Reclassify → FE` и оставить статус 🟥 New для них.
- **Не дублировать обсуждение в чате.** Всё в History. Чат теряется, файл — нет.
- **Не делать silent breaking changes в API.** Если меняется response — обновить `Acceptance criteria` + предупредить FE строкой в History.
- **Не комитить миграции без upgrade-pathа для существующих данных.** Если есть hot-prod данные / тестовые записи у Антона / Marina / Sarah — миграция должна их пережить. Иначе QA сразу 🟥 Reopened.
- **Не пушить деплои в пятницу вечером** перед QA-выходными без согласования.

## Что нужно от FE

Если для воспроизведения / диагностики нужен пример payload от FE — попросить через History строку:

```markdown
- 2026-05-27 · Иван · нужен пример request body, который FE отправляет в POST /api/bookings
  с pets > 0. Сейчас в логах только без pets, не могу воспроизвести.
```

Claude / Антон ответят строкой в той же секции с конкретным curl'ом или JSON'ом.
